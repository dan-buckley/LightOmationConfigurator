# 1.2.3 Matrix Light Support

| Field | Detail |

| ID | 1.2.3 |
| Layer | Data Management |
| Status | Done |
| Depends On | 1.2.1, 1.2.2 |

## Purpose

Extend segment config entries to support 2D matrix lights by adding Y-axis coordinates. Update the fingerprint algorithm to correctly distinguish matrix segments that differ only in their Y range. Add `light_type` and `shortcode` columns to `lights` to record each light's physical layout category.

## Background

WLED matrix segments carry both X coordinates (`start`/`stop`) and Y coordinates (`startY`/`stopY`). The Small_MATRIX light (48×32, 1536 LEDs) uses presets where different presets address different Y regions — for example preset 3 "Swirl" uses `start=0, stop=64, startY=0, stopY=16` while all other presets use `start=0, stop=48, startY=0, stopY=32`. Without Y coordinates in the fingerprint, these distinct layouts are treated as identical (both have the same X range), which causes incorrect deduplication.

Additionally, WLED matrix segments include rendering flags per preset:
- `rY` — reverse Y axis
- `mY` — mirror Y axis
- `m12` — transposition mode (row/column/block)
- `tp` — transpose flag

These flags are per-preset artistic choices, not physical layout properties. They are already preserved in `preset_data` JSON and do not need dedicated columns.

## Data Model Changes

### `light_segment_config_entries` — add columns

```
start_y   INTEGER   nullable   -- Y start coordinate; null for 1D strip segments
stop_y    INTEGER   nullable   -- Y stop coordinate; null for 1D strip segments
colour    TEXT      nullable   -- JSON "[R,G,B]" characteristic colour for this segment
```

### `lights` — add columns

```
light_type          TEXT   DEFAULT 'strip'   -- strip | matrix | multi_segment | composite
shortcode           TEXT   nullable           -- 2–5 char abbreviation e.g. "RB", "DEE", "SM"
preset_slot_scheme  TEXT   nullable           -- JSON defining ID range allocations per preset type
```

## Migration

New Alembic migration (`batch_alter_table` for SQLite compatibility) adding:
- Three columns to `light_segment_config_entries`
- Three columns to `lights`

Existing rows: `start_y`, `stop_y`, `colour` default to null; `light_type` defaults to `'strip'`; `shortcode` and `preset_slot_scheme` default to null.

## Fingerprint Update

**Current fingerprint** (1.2.1):
```python
json.dumps(sorted([(entry.start, entry.stop) for entry in active_entries]))
```

**Updated fingerprint** (1.2.3):
```python
json.dumps(sorted([
    (entry.start, entry.stop, entry.start_y or 0, entry.stop_y or 0)
    for entry in active_entries
]))
```

This ensures matrix presets with identical X ranges but different Y ranges are treated as distinct configs.

## Scan Changes

`_scan_presets_json_raw` (in `imports.py`) updated to:
- Extract `startY` and `stopY` from each segment object (fallback to `None` if absent)
- Pass Y values through to the scanned config entry

`_upsert_hardware_default_config` updated to:
- Set `start_y=None`, `stop_y=None` for all entries derived from 1D cfg strips

## Light Type Auto-detection

During `extract-profile` (applying a cfg to update a light's layout):
- If `cfg["hw"]["led"]` contains a `matrix` sub-object → set `light_type='matrix'`
- Otherwise leave `light_type` unchanged (do not overwrite a manually set value)

## API Changes

No new endpoints. All existing segment config and light endpoints updated to include new fields in request/response schemas.

Response schema additions:
- `SegmentConfigEntryOut`: add `start_y`, `stop_y`, `colour` (nullable)
- `LightOut`: add `light_type`, `shortcode`, `preset_slot_scheme`

## UI Changes

- `SegmentConfigList`: show `Y: {start_y}–{stop_y}` alongside `LEDs: {start}–{stop}` for entries where Y values are present
- `LightForm`: add `light_type` dropdown (options: strip / matrix / multi_segment / composite), `shortcode` text field, `preset_slot_scheme` JSON textarea
- Segment editor: unchanged (Y ranges are not editable via the reference segment editor; they come from scan/import)

## Key Rules and Constraints

- `start_y`/`stop_y` are only populated for matrix lights; null for all 1D strip types
- `colour` is populated by Module 1.5 (characteristic colour detection); nullable at this stage
- `light_type` defaults to `strip` for all existing lights; auto-detected from cfg where possible
- Matrix rendering flags (`rY`, `mY`, `m12`, `tp`) are per-preset artistic choices stored in `preset_data` — they are not stored in segment config entries

## Acceptance Criteria

- [ ] Migration adds all new columns without affecting existing data

- [ ] `shortcode` and `preset_slot_scheme` fields are editable on the light form
