# 2.3 Validation Engine

| Field | Detail |
|---|---|
| ID | 2.3 |
| Layer | Processing |
| Status | Backlog |
| Depends On | 2.2 |
| Milestone | M2 |

## Purpose

Check a generated `presets.json` file against a set of defined rules before it is exported or deployed. Produce a structured validation report that clearly identifies any issues and their severity.

## Responsibilities

- Run all validation checks against a generated file and its associated light profile
- Classify each check result as Pass, Warning, or Fail
- Return a structured report listing each check with its result and any relevant detail
- Block export and deployment if any check returns Fail (Warnings are non-blocking)

## Out of Scope

- Generating the file (Module 2.2)
- Exporting or deploying the file (Modules 3.1, 3.2)
- Validating imported files (import validation is format-only, performed in Module 1.2)

## Inputs

| Input | Description |
|---|---|
| `generated_file_id` | ID of the record in `generated_files` to validate |

## Outputs

| Output | Description |
|---|---|
| `validation_report` | Structured list of check results; overall status of Pass, Warning, or Fail |

## Validation Checks

| Check | Severity | Rule |
|---|---|---|
| Valid JSON structure | Fail | The file parses as valid JSON |
| Root key `"0"` present | Fail | WLED requires `"0": {}` at the root |
| Preset IDs are unique | Fail | No two presets share the same key in the root object |
| Preset IDs are positive integers | Fail | All keys (except `"0"`) parse as positive integers |
| Segment count matches light profile | Fail | Each segmented preset uses the same number of segments as the light profile |
| Segment total matches light total | Fail | The sum of all active segment lengths equals the light's total LED count |
| Segment ranges are contiguous | Fail | No gaps between segments; no LEDs outside `0` to `total_leds` |
| Playlist preset IDs exist | Fail | Every ID referenced in a playlist's `ps` array exists as another preset in the file |
| Segment count mismatch (partial) | Warning | A preset has fewer segments than the light profile (excess segments inactive) |
| Quick-label uniqueness | Warning | Two presets share the same `ql` value |
| Large total LED count delta | Warning | Generated LED total differs from light profile total by more than 5% |

## Key Rules and Constraints

- Validation is read-only; it does not modify any database record
- A Fail result on any check sets the overall report status to Fail
- A Warning with no Fail sets the overall status to Warning
- The export and deployment endpoints must call the validation engine and refuse to proceed if the result is Fail
- Validation must be callable independently (e.g. via a dedicated API endpoint) without triggering export or deployment

## API Endpoints

| Method | Path | Description |
|---|---|---|
| POST | `/api/v1/validate/{generated_file_id}` | Run validation and return the report |

## UI

- Validation report displayed after generation and before the export/deploy action
- Each check shown with a pass/warning/fail indicator and detail text
- Overall status clearly prominent; export and deploy buttons disabled on Fail

## Acceptance Criteria

- [ ] A correctly generated Small Rainbow file passes all checks
- [ ] A file with a missing `"0"` key returns Fail on that check
- [ ] A file with a broken playlist reference returns Fail on the playlist check
- [ ] A file with a segment count mismatch returns the correct Fail or Warning as defined
- [ ] Export endpoint refuses to proceed if validation returns Fail
- [ ] Validation report is returned in a consistent structured format

## Open Questions

- Should validation results be stored in the database alongside the generated file record?
- Should users be able to override a Fail and force an export with an explicit acknowledgement?
