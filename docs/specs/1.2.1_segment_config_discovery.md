## Background

A single WLED device can use different segment layouts across its presets. For example a 182-LED Rainbow light might have:
- A full-strip preset using one segment (0–182)
- A 7-zone playlist that divides the strip into seven equal segments
- A 5-zone variant

This means "light has segments" is not a single static fact — a light has **multiple named segment configurations**, one of which is active per preset. Module 1.1 models the reference/default layout. This module introduces named configurations so that master presets and the transposition engine know exactly which layout each preset expects.

## Responsibilities

- Add `light_segment_configs` and `light_segment_config_entries` tables via Alembic migration
- When a `cfg.json` extract-profile is applied, also write a named config ("Hardware default") in addition to updating `light_segments`
- When a `presets.json` is imported, scan it for unique segment configurations and persist each distinct one as a named config for the associated light
- Provide CRUD API for segment configs (list, get, create, update, delete)
- Display discovered configs per light in the Lights page UI
- Add `segment_config_id` to `master_presets` table (nullable at this stage; required from Module 1.3 onward)

```
LightSegmentConfig
  id            INTEGER PK
  light_id      INTEGER FK → lights.id
  name          TEXT NOT NULL          -- e.g. "Hardware default", "7 zones", "Full strip"
  source_import_id  INTEGER FK → imported_files.id  (nullable — null if manually created)
  created_at    DATETIME

LightSegmentConfigEntry
  id            INTEGER PK
  config_id     INTEGER FK → light_segment_configs.id  (cascade delete)
  segment_index INTEGER NOT NULL
  name          TEXT                   -- nullable
  start_led     INTEGER NOT NULL
  stop_led      INTEGER NOT NULL
  -- Extended in Module 1.2.3:
  start_y       INTEGER                -- nullable; Y start for matrix lights
  stop_y        INTEGER                -- nullable; Y stop for matrix lights
  colour        TEXT                   -- nullable; JSON "[R,G,B]" characteristic colour (set in Module 1.5)
```

`master_presets.segment_config_id` INTEGER FK → `light_segment_configs.id` (nullable)

## Segment Discovery from presets.json

A WLED `presets.json` is a flat JSON object keyed by preset ID (integer as string). Each preset value may contain a `seg` array. Each entry in `seg` has at minimum `start`, `stop` (exclusive), and an implied index by array position. Active segments have `on: true` (or the field is absent — treat absence as active).

Deduplication: two presets share a config if their active segment arrays are identical (same count, same start/stop for each, in order). The first preset whose segment set is seen gets its name used as the config name.

**Fingerprint algorithm** (see also Module 1.2.3 for matrix extension):
```python
# 1D fingerprint (this module)
json.dumps(sorted([(start, stop) for (start, stop) in active_segs]))

# Matrix fingerprint (added in Module 1.2.3)
json.dumps(sorted([(start, stop, start_y or 0, stop_y or 0) for ... in active_segs]))
```

Special cases:
- Presets with no `seg` field are skip-scanned (they inherit the device state — no config to extract)
- Playlists (`playlist` key present) have no segments of their own — skip
- Button presets (`n` starts with "~") — still scan for segments if present

## API Endpoints

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/lights/{light_id}/segment-configs` | List all configs for a light |

| GET | `/api/v1/lights/{light_id}/segment-configs/{config_id}` | Get config with entries |

## UI

- **Lights page — Segment Configs tab** (alongside the existing segment editor): lists all named configs for the selected light; shows segment ranges per config; allows renaming and deleting; shows the source import where known
- **Import page** — after a `presets.json` upload, a "Scan for segment configs" button triggers the scan endpoint and shows a summary of how many unique configs were found

## Key Rules and Constraints

- Config names must be unique per light
- A config cannot be deleted if any master preset references it (returns 409)
- Scanning is idempotent: re-scanning the same import does not create duplicate configs (matched by segment fingerprint)
- Manually created configs are not touched by scan
