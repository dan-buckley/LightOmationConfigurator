# 3.2 WLED Network Connector

| Field | Detail |
|---|---|
| ID | 3.2 |
| Layer | Output |
| Status | Backlog |
| Depends On | 1.2, 3.1 |
| Milestone | M3 |

## Purpose

Communicate directly with WLED devices on the local network to fetch current configuration and preset files, and to push generated files to the device. All fetched files are stored as imports. All push operations are recorded in deployment history.

## Responsibilities

- Test connectivity to a WLED device by IP address
- Fetch `presets.json` from a device and store as an import record (delegates to Module 1.2)
- Fetch `cfg.json` from a device and store as an import record (delegates to Module 1.2)
- Push a validated generated `presets.json` to a device
- Record every push in `deployment_history` with result
- Provide a connection status indicator per light

## Out of Scope

- WLED device discovery via mDNS or network scan (Later Scope)
- Bulk push to multiple devices in one action (Later Scope)
- Fetching or pushing other WLED endpoints beyond `presets.json` and `cfg.json`

## WLED API Endpoints Used

| Action | WLED Endpoint | Method |
|---|---|---|
| Fetch `presets.json` | `http://{ip}/presets.json` | GET |
| Fetch `cfg.json` | `http://{ip}/cfg.json` | GET |
| Push `presets.json` | `http://{ip}/upload` | POST (multipart) |
| Test connectivity | `http://{ip}/json/info` | GET |

## Application API Endpoints

| Method | Path | Description |
|---|---|---|
| GET | `/api/v1/network/ping/{light_id}` | Test connectivity to device |
| POST | `/api/v1/network/fetch/{light_id}` | Fetch presets.json and cfg.json from device |
| POST | `/api/v1/network/push/{light_id}` | Push generated file to device |
| GET | `/api/v1/network/deployments` | List deployment history (filterable by light) |

## UI Screens

- **Network panel** (per light) — shows current IP, connectivity status (live ping), buttons to Fetch and Push; last fetch and last push timestamps; link to deployment history
- **Deployment history** — list of all pushes per light with timestamp and result

## Key Rules and Constraints

- The device IP address must be set on the light profile before any network operation is attempted
- A fetch operation always stores the result as a new `imported_files` record before returning; it never silently discards fetched data
- A push must be refused if the generated file fails validation (calls Module 2.3)
- A push must be refused if no fetch has been performed for this light since the last push (requires at least one backup on record)
- Network timeouts must be short (5 seconds) and return a clear error rather than hanging
- All network calls are made from the backend; the frontend never contacts WLED directly

## Acceptance Criteria

- [ ] Ping returns online/offline status for RB Proto and Small Rainbow
- [ ] Fetch stores both `presets.json` and `cfg.json` as new import records
- [ ] Push sends the correct generated file to the device and records the result in `deployment_history`
- [ ] Push is refused if validation fails; user sees the validation failure
- [ ] Push is refused if no prior fetch exists for this light
- [ ] Network timeout (unreachable device) returns a clear error within 5 seconds
- [ ] Fetched files are accessible in import history

## Open Questions

- Should the push endpoint reboot the WLED device after upload (WLED supports `/win&RB` for reboot)?
- What should happen if the push succeeds but the device returns an unexpected response code?
